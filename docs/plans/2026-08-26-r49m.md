## User Request

### Requested result
Fix the pane-header rename input race that makes `test/e2e-browser/specs/title-sync-convergence.spec.ts:217` ("pane header rename converges the sidebar") fail deterministically on cloud e2e runs: after `renameInput.fill(NEW_NAME)` + Enter, the pane header must converge to exactly the typed name within its 10s timeout. The observed dump showed the header still rendering the OLD title preceded by the provider-icon letter badge (`C` + `convergence-alpha`, misread upstream as a "duplicated first character"), while all aria-labels stayed correct — i.e. the typed rename never landed at all.

### Explicit constraints
- Root cause is at the event/focus delivery layer, not state sync: the rename input is a purely local controlled input (no server echo, no props→state sync, no remount keys), so typed text can only be lost by focus diversion. Playwright 1.58's `fill()` is two-phase (in-page `select(); focus()`, then trusted `insertText` after a CDP round-trip); under Cloud Run 2-CPU latency, TerminalView's background `term.focus()` paths (active-pane rAF effect `TerminalView.tsx:1272-1285`, coalesced layout flush `:1711-1713` fed by the mount flush `:2300`, scheduled via the rAF-coalesced `layout-scheduler.ts`) can land inside that window and divert the insert into xterm's helper textarea, where it is consumed as PTY input and lost. The subsequent Enter press re-focuses the input and commits the unchanged prefill — a no-op rename — so the header keeps the old title forever.
- Reproduces deterministically under Cloud Run 2-CPU task latency; not reachable locally at normal timings.
- Untouched by PR #672 (that fix was e2e-infra only, zero `src/` changes).
- Repository rules: Red-Green-Refactor TDD; unit + e2e coverage; fix the system over the symptom; a11y must not regress (the rename input keeps `aria-label="Rename pane"`).
- The failing spec itself must NOT be edited (no timeout bumps, no typing-speed changes) — it is the regression pin.

### Accepted tradeoffs and residuals
- The full QA gate baseline contains three pre-existing, unrelated `test/unit/vite-config.test.ts` getNetworkHost failures, accepted by identity under the baseline ledger; this work neither fixes nor regresses them.
- `FRESHELL_E2E_BACKEND` is unset on the host, so e2e verification runs on the default local backend. Local timings do not reproduce the cloud race; the deterministic proof of the fix is the new unit/component tests that simulate the focus-diversion window directly, plus a clean local run of the affected spec. A cloud full-suite re-run remains the ultimate confirmation and is outside what this worktree can control.

**Goal:** A pane-header rename started by double-click commits exactly what the user typed, even when background terminal refocuses are queued behind a saturated main thread, so the cloud e2e sidebar-convergence test converges.

**Architecture:** Two focused production changes. (1) A small focus policy module, `shouldYieldProgrammaticTerminalFocus()`, tells TerminalView's two *background* programmatic `term.focus()` paths to yield whenever an editable element outside xterm's own helper textarea holds DOM focus — user-driven focus calls (search close, mobile toolbar) are untouched. (2) The pane-rename commit treats the server's transient `pane not found` no-op (the client-pushed layout mirror hasn't landed yet, a documented automation-contract response) as retryable with a short bounded backoff instead of immediately stranding the open editor.

**Tech Stack:** React 18, Redux Toolkit, TypeScript, Vitest 3 + Testing Library (jsdom), Playwright (e2e verification only).

```ts
// src/components/terminal/focus-policy.ts
/**
 * TerminalView's background focus paths (the active-pane rAF effect and the
 * coalesced layout flush) can fire long after they were requested — under a
 * saturated main thread, exactly while the user has started inline editing
 * elsewhere in the pane chrome (kata r49m: pane-header rename). Stealing
 * focus mid-edit diverts the pending keystrokes into xterm's helper textarea,
 * where they are consumed as PTY input and silently lost.
 *
 * The policy: programmatic terminal focus yields to any text-entry element
 * outside xterm's own helper textarea. Non-text controls (buttons,
 * checkboxes) do not yield, so click-to-activate typing UX is unchanged.
 * User-driven refocus paths (search close, mobile toolbar) never consult this.
 */
const XTERM_HELPER_TEXTAREA_CLASS = 'xterm-helper-textarea'

const NON_TEXT_INPUT_TYPES = new Set([
  'button',
  'checkbox',
  'color',
  'file',
  'hidden',
  'image',
  'radio',
  'range',
  'reset',
  'submit',
])

function isTextEntryControl(el: Element): boolean {
  if (el instanceof HTMLTextAreaElement) return true
  if (el instanceof HTMLInputElement) {
    return !NON_TEXT_INPUT_TYPES.has((el.type || 'text').toLowerCase())
  }
  return false
}

export function shouldYieldProgrammaticTerminalFocus(doc: Document = document): boolean {
  const el = doc.activeElement
  if (!el || el === doc.body) return false
  if (
    el instanceof HTMLTextAreaElement &&
    el.classList.contains(XTERM_HELPER_TEXTAREA_CLASS)
  ) {
    return false
  }
  if (isTextEntryControl(el)) return true
  return el.closest('[contenteditable]:not([contenteditable="false"])') !== null
}
```

```ts
/**
 * Human pane renames PATCH /api/panes/:id. The server's layout mirror is
 * client-pushed (ui.layout.sync, 200ms-1000ms+ debounce after a fresh
 * resume), so a fast rename can hit the documented Node-parity no-op
 * 200 {message:'pane not found'} even though the pane plainly exists
 * (kata r49m companion race: the open editor was stranded with a stale
 * error). Only that transient no-op is retried; it is the one response
 * that provably means "mirror not landed yet" rather than a user error.
 */
export type PaneRenameResponse =
  | { data?: { paneId?: string; tabId?: string; tabRenamed?: boolean }; message?: string }
  | null
  | undefined

export type PaneRenameResult =
  | { ok: true; response: PaneRenameResponse }
  | { ok: false; message: string }

const MIRROR_NOT_FOUND_MESSAGE = 'pane not found'
const DEFAULT_RETRY_DELAYS_MS: readonly number[] = [200, 400, 800]
const GENERIC_FAILURE_MESSAGE = 'Failed to rename pane'

export async function renamePaneWithMirrorRetry(
  paneId: string,
  name: string,
  opts: {
    patch: (path: string, body: unknown) => Promise<PaneRenameResponse>
    sleep?: (ms: number) => Promise<void>
    retryDelaysMs?: readonly number[]
  },
): Promise<PaneRenameResult> {
  const sleep = opts.sleep ?? ((ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms)))
  const retryDelaysMs = opts.retryDelaysMs ?? DEFAULT_RETRY_DELAYS_MS
  for (let attempt = 0; ; attempt++) {
    const response = await opts.patch(`/api/panes/${encodeURIComponent(paneId)}`, { name })
    if (response?.data?.paneId === paneId) {
      return { ok: true, response }
    }
    const message =
      typeof response?.message === 'string' && response.message ? response.message : GENERIC_FAILURE_MESSAGE
    const retryable = message === MIRROR_NOT_FOUND_MESSAGE && attempt < retryDelaysMs.length
    if (!retryable) return { ok: false, message }
    await sleep(retryDelaysMs[attempt])
  }
}
```
