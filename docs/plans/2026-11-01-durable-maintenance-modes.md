## User Request

### Requested result
Implement the three managed-runtime update modes: default updates the web/client without restarting the durable supervisor or resetting managed coding sessions; `--all` updates the web/client and durable runtime; `--durable-only` updates durable components while leaving the web/client unchanged. Also fix the pre-existing managed-provider qualification compile failure in a dedicated worktree so tests can run, then continue the update-mode implementation.

### Explicit constraints
- Require the user to say “APPROVED” verbatim before either reset-capable mode, based on the mode/action category and without compatibility analysis.
- Both reset-capable modes reset managed coding sessions by default after approval, preserve conversation history, and attempt to reopen saved conversations against the updated runtime.
- Default mode reminds the operator that the supervisor and managed sessions were not restarted and that reset-capable updates require verbatim approval.
- Remove the existing broad approval restriction for ordinary web/client restarts; do not replace it with another web/client approval rule.
- Ensure ordinary web/client maintenance cannot indirectly restart the durable supervisor.
- Use the-usual workflow.
- Fix the baseline compile failure in the dedicated worktree under the user's explicit exception, then continue the requested update-mode implementation.

### Accepted tradeoffs and residuals
- An approved update may interrupt active coding sessions; saved history remains and reopening is attempted, but recovery is not guaranteed. Manually reopening or porting sessions afterward is acceptable if needed.

## Goal

Operators can update the web/API server and served client without restarting the durable supervisor or resetting managed coding sessions, update the web/client and durable runtime together, or update the durable runtime alone. Every mode runs in a discoverable transient systemd user service under one per-user exclusive update lock, so the work and its durable logs survive caller loss and concurrent update modes cannot overlap. The two reset-capable modes require an exact APPROVED line, preserve conversation history, reset only coding-provider souls whose authoritative `desired_state` is `running`, and attempt reopening saved conversations on the updated runtime. Souls already marked stopped are never stopped again or reopened; an unverified prior Stop blocks replacement and is reported without retrying or polling it.

## Architecture

Add pnpm run update:managed-runtime with a web/client default and explicit --all and --durable-only modes. Each invocation uses a discoverable transient systemd user service. Its small Node bootstrap creates the durable JSONL logger, then invokes `flock -n -E 75`; on lock contention it records a structured `update.lock_contention` event and exits 75 before owner/build/control/service work. On success it starts the actual worker as the locked child, with `flock` holding the exclusive per-user lock for the worker's full lifetime. The wrapper prints the unit name, journal commands, and durable JSONL path before handing off; it never pipes worker stdout/stderr back through the caller. The bootstrap and worker receive the selected mode as a nonsecret internal argument and, only for reset modes, an owner-only mode-0600 approval-file path. Only the worker reads and revalidates the exact raw `APPROVED` line, deletes the file, and then begins owner/effect work. Default needs no approval file. Use absolute Node, tsx, script, working-directory, pnpm, Cargo, and Docker paths, plus an explicit minimal allowlisted toolchain environment; do not forward the caller's general environment or secrets.

Resolve the supported systemd user-unit owner and its artifact/resource manifest before staging. Before any web restart, inspect the effective installed systemd dependency graph and refuse if an activation edge could start or restart the supervisor. The web unit drop-in uses ordering-only After= so ordinary web/client maintenance cannot activate or restart the supervisor. The updater explicitly sequences any supervisor and web starts it needs.

The default worker builds and stages the web server with its `managed-runtime-v1` bridge and the served client, installs both, and restarts only freshell-rust.service. Before submitting the transient unit, the wrapper prints the required reminder that supervisor/sessions were not restarted and reset modes require exact APPROVED. The worker makes no supervisor control request, does not stop managed sessions, and does not restart or activate the durable supervisor. Its worker and readiness result continue to completion if the restart kills the caller PTY; logs and unit status remain available independently.

Both reset modes require exact approval. They stage all selected artifacts and compare the candidate's compiled registry schema with the current installation schema before stopping any service. The candidate supervisor exposes a side-effect-free schema-version command that prints compiled `SCHEMA_VERSION` without opening a registry; the current `installation.schema_version` is read through a read-only SQLite connection. This feature is migration-free and reuses schema-19's existing `commands` journal for successful Reopen incarnation idempotency. Reopen uses the control request ID as the launch command ID; its digest includes the expected stopped revision and saved context; the command row, incarnation association, and stopped-to-running CAS commit atomically. Exact replay is checked before the now-advanced revision and returns the existing incarnation. Pending revocation commits no new command/incarnation or revision and may retry with a fresh ID. Missing native identity is reported as `unavailable` by the updater without dispatching Reopen. The journal does not provide an exact durable replay promise for every failure or unavailable result. Any candidate/current schema mismatch is refused before the web/API stop and points to the existing verified-backup/upgrade procedure.

After schema preflight, reset modes stop the web/API unit to close UI create/retry ingress, take one final inventory over the still-running supervisor's exact control socket, and first check every already-stopped coding soul. A `desired_state=stopped` soul is never stopped or reopened; if final inventory does not already prove its runtime `VerifiedEmpty`, abort before issuing any new Stop, without re-Stopping or indefinite polling, and report the existing pending user Stop. If empty, preserve its stopped intent. Then derive the fixed reset set from coding-provider souls whose authoritative `desired_state=running`, including desired-running provisioning/pre-native/recovering souls regardless of incarnation launch state. Send exactly one revision-fenced Stop per target, using its request ID only as a correlation ID because Stop is not deduplicated by request ID. After every selected Stop is verified empty, they stop the supervisor, install selected artifacts, start the supervisor and wait for its control socket, then start the web/API unit and wait for readiness and callback-socket availability before attempting Reopen. Build Reopen candidates only by intersecting saved references with the updater's successfully stopped target set. A new supervisor admin CLI performs Inventory, typed Stops, and revision-fenced Reopen directly over the control socket. Reopen uses the web-owned MCP capability callback, first retries/confirms the exact prior Stop and grant revocation, and does not advance the stopped intent revision or create an incarnation while revocation is unresolved.

The new Reopen operation uses the stopped soul's saved launch/resume context, native identity, and provider store to create a new incarnation with the current runtime. A missing native ID keeps the soul in the reset set but yields an updater-reported unavailable result without an Reopen dispatch. An unresolved grant revocation yields a typed pending result at the same stopped revision; the caller can retry with a fresh request ID. A repeated successful request ID returns the same incarnation without creating another one, using the existing command journal and an atomic stopped-to-running CAS. Do not fabricate a soul, native ID, or store. Keep the current Inventory/Stop protocol version and wire contract; send additive Reopen only to the updated supervisor. The compile repair is a prerequisite commit.
