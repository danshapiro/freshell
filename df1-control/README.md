## Architecture

- `~/.freshell/df1/items.json` — work queue; states:
  `queued → claimed → in-progress → review → (merged-unverified-e2e | done)`,
  plus `blocked(dep)`, `needs-human`, `failed`, `host-limited`, `done`.
- `~/.freshell/df1/events/launches.jsonl` — append-only launch/kill/lease/merge ledger
  (also GATE-08 parity-receipt raw material).
- `~/.freshell/df1/status/<ID>.json` — per-item agent snapshot (phase, sha, heartbeat,
  note, tests, decisions). `updated` epoch doubles as the reaper heartbeat.
- Leases (`df1-control/scripts/acquire.sh`): atomic mkdir leases w/ TTL heartbeats,
  stale-reaping, and live system guards (MemAvailable ≥ 4G, load1 ≤ 40, disk ≥ 100G).
  | lane | cap | guards |
  |---|---:|---|
  | agent | 32 | total swarm size (ramp 8→16→24→32) |
  | provision | 2 | npm ci + first cargo build |
  | cargo | 3 | heavy cargo builds/tests |
  | pw | 4 | Playwright (RAM-bound; also system-guarded) |
  | sandbox | 2 | destructive docker suites |
  | gate | 1 | coordinated repo suite (gatekeeper only) |
- `df1ctl.py` — claim/update/requeue/set-state/report/events/item (see `--help`-style
  docstring at top of script).

## Agent roles (prompt templates in prompts/)

- **worker** (one per item, fire-and-forget): sees only its prompt + repo files.
  Commits at phase boundaries so a killed agent's worktree IS the checkpoint; a
  replacement resumes in place. Never pushes, never PRs, never edits the checklist.
- **verifier** (one per completed item): re-runs the claimed green commands at the
  claimed SHA; PASS/FAIL one-liner. The anti-hallucination layer.
- **gatekeeper** (one per merge batch of ~10): merges verifier-PASSed branches into
  `df1/integration`; per-branch spec ordering runs (pre-merge fail → post-merge green);
  batch gates (workspace cargo tests, typecheck, lint, canary set, coordinated suite).
- **reaper** (periodic): mechanical kill criteria (stale heartbeat > 60m, phase
  timeouts, review over-budget) → KILLED event + requeue. Never deletes worktrees.

## Deferred-Playwright policy (agreed 2026-08-08)

Main-phase workers mostly skip Playwright; one mass close-out campaign at the end.
Three NON-NEGOTIABLE carve-outs:
1. **Spec-deliverable items** (`pwMode: self-verify`, assigned per item at launch —
   e.g. the 29 rust-blind specs and other "Missing: re-target/PW-RUST spec only"
   PARTIALs) must run their own spec RED→green before completion.
2. **Canary set per merge batch** (gatekeeper): `harness-01-rust-server`,
   `terminal-lifecycle`, `settings-persistence-split`, `restore-matrix`,
   `server-restart-recovery`, `session-directory-matrix`, `multi-client`,
   `browser-pane` — both server kinds. Attribution window stays ~10 merges, not 160.
3. **Ordering proof at merge time**: a branch's new/changed specs run against the
   pre-merge integration tip (expect failure-per-annotation), then post-merge (green) —
   preserves the checklist's fail-before/pass-after semantics at batch granularity.

Items merged in the main phase are `merged-unverified-e2e`, NEVER `done`. Close-out
converts them one by one. Close-out also runs GATE-01's full-suite-both-kinds bar and
doubles as the mass-debug phase: failures auto-attribute to items via the ledger and
requeue as df1 follow-up tasks.

## Anti-conflict conventions

- **Checklist annotations via evidence files**: workers write
  `docs/plans/df1-evidence/<ID>.md` in their own branch (same annotation style as the
  checklist). A final consolidation pass merges them into the checklist. Direct
  checklist edits by workers are forbidden (160-way merge conflict otherwise).
- **Matrix spec registration**: until an auto-registration enabler lands, adding a
  `rust-chromium` leg means appending one regex line to `MATRIX_SPECS` in
  `test/e2e-browser/playwright.config.ts` — gatekeepers resolve the additive conflicts
  by unioning. (Proposed wave-0 enabler: per-spec registration so the shared edit
  disappears entirely — see open decisions.)
